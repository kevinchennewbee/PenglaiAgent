# Penglai 0.4 IM Bridge

A small Python module that lets the **existing 0.3 Feishu / WeChat IM adapters**
talk to the **0.4 TypeScript Host** instead of the old Python Runtime Hub.

The 0.3 IM adapters are Python; the 0.4 Host is TypeScript. Rather than rewrite
the adapters, this bridge is a drop-in replacement for the old
`runtime.prompt(...)` call site. Everything else in the adapter (IM auth,
message routing, reply formatting) stays unchanged.

## Files

- `im_bridge.py` — the bridge module. Copy it next to your adapter, or add this
  directory to `PYTHONPATH`.

## How to integrate

In your existing 0.3 IM adapter (e.g. `penglai_feishu_app.py`,
`penglai_im_launch.py`), replace the old Runtime Hub call:

```python
# OLD (0.3): talked to the Python Runtime Hub
# runtime.prompt(text, workspace=...)

# NEW (0.4): talk to the TS Host over loopback JSON-RPC
from im_bridge import PenglaiHostBridge

bridge = PenglaiHostBridge(port=14169)  # reads ~/.penglai/host.token automatically

# When an IM message arrives:
reply = bridge.prompt(text=user_message, workspace_path="/path/to/project")
send_to_im(reply)
```

For non-blocking use (so the IM adapter isn't blocked while the agent runs),
use the callback form:

```python
bridge.prompt_async(
    text=user_message,
    workspace_path="/path/to/project",
    callback=lambda reply: send_to_im(reply),
)
```

### Prerequisites

1. The TS Host must be running: `npm run serve` (binds `127.0.0.1:14169`).
2. The host token exists at `~/.penglai/host.token` (auto-created on first
   `serve`). The bridge reads it; no manual config.
3. At least one model profile has its API key env var set
   (`GROK_API_KEY` / `DEEPSEEK_API_KEY` / `ZAI_API_KEY` / `OPENAI_API_KEY`).
   `prompt()` auto-picks the first usable profile.

## Security

- **Loopback only.** The Host binds `127.0.0.1`; the bridge only ever talks to
  `127.0.0.1`. No IM traffic leaves the machine — the IM adapter is still the
  only thing that reaches the network.
- **Token-gated.** Every `/api` call carries `Authorization: Bearer <token>`.
  The token is generated by the Host and stored with `0600` perms.
- **`chat_safe` policy applies to IM by default.** Per
  `docs/0.4/01-CONSTITUTION.md §7.2` and `packages/host/src/policy.ts`, the IM
  surface is an untrusted channel and must run under the `chat_safe` profile
  (read-only: `read` allowed; `write` / `edit` / `bash` denied). The Host
  enforces this at the Boundary; the bridge just forwards text and never
  bypasses policy. Sensitive key paths (`.env`, `*.pem`, `id_rsa`, …) are
  denied under all profiles.

## Design (M4): intentionally simple

This bridge is deliberately minimal:

- **Polling, not WebSocket.** `prompt()` calls `session.prompt` then polls
  `session.get` every 2 s until the session leaves the `running` state. This is
  fine for IM's low message rate and keeps the bridge dependency-free (stdlib
  `urllib` only — no `requests`, no `websockets`).
- **No streaming.** The full assistant reply is returned only after the turn
  completes. IM doesn't need token streaming.
- **No second loop.** Per the constitution's Single Loop Axiom, the bridge
  never runs the model or tools itself — it only forwards prompts to the Host's
  one Agent Core.

**Upgrade later:** swap the polling in `prompt()` for a WebSocket subscription
on `/ws` to get `assistant.delta` events as they stream, giving IM users
token-by-token progress. The Host already speaks WS; the bridge just doesn't
use it yet.
